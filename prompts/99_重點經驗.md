## 2026-08-01｜交付 docx 是「有狀態」檔案——整份重轉會靜默毀掉使用者的審查註解（多會期併行事故）

### 現象
使用者在 `reports/final/整合測試報告.docx` 用 Word 註解逐案審查，累積 26 則。同一時間**另一個會期**跑 `md_to_docx` 從 md 重轉，產出同內容但**註解為 0** 的 `整合測試報告_已通過.docx`，兩份並存於交付目錄；期間雙方還各自改了 `WBS_ALIAS`。差一步就把 26 則審查軌跡連同使用者手調的表格欄寬一起洗掉，而且**不會有任何錯誤訊息**。

### 原因
1. **md 不是 docx 的完整來源**。docx 裡有兩樣東西只存在於 docx：使用者的 Word 註解、手調欄寬。用「md → 重轉」當成更新手段，等於預設 docx 可從 md 完全重建 —— 對已進入人工審查的交付檔，這個前提不成立。
2. **檔名不唯一**。`build_split_reports.py` 輸出 `整合測試報告_已通過.md`，`md_to_docx` 預設同名輸出 → 必然產生 `整合測試報告_已通過.docx`；但使用者實際交付的檔名是 `整合測試報告.docx`。兩個名字讓「同一冊」有兩份不同狀態的實體，誰都不知道哪份是真的。
3. **沒有併行約定**。兩個會期都認為自己擁有這些路徑。

### 對策
- **交付檔一律就地 patch**（python-docx 改段落／表格／插圖），不重轉。本次 42 案審查回填、63 張補圖、章節拆分全部是就地做的，註解與欄寬全保留。
- **把「可重建的狀態」外部化**：審查結果寫進 `reports/final/審查核可紀錄.json`（含意見原文、日期、審查人），`build_split_reports.py` 讀它決定標「已審查」或「【待審】」→ **md 可以安全重建而不遺失審查結果**。註解本身仍只在 docx，所以上一條照舊。
- **加機械防護，不要只寫規則**：`md_to_docx.py` 偵測目標 docx 含 Word 註解就中止並回 **exit 1**（需 `--force`）。規則會被忘記，exit 1 不會。
- 規則寫入 `CLAUDE.md`〈交付報告產製規則（多會期併行必讀）〉：檔名對照表唯一化、同時只允許一個會期寫 `reports/final|review` 與那三支工具、動工前查 `~$*.docx` 鎖檔與目標 mtime。
- **偵測併行的方法**：比對 `~/.claude/projects/<專案>/*.jsonl` 的 mtime 找出還活著的會期；用關鍵字出現次數判斷誰在動哪支工具。⚠ **jsonl 內的 timestamp 是 UTC，要 +8 才是本地時間**，否則會誤判「那個會期兩天前就停了」。
- 附帶教訓：`WBS_ALIAS` 這類**顯示層別名**不可把不同測試範圍對到同一個名字（`RT-業主`＝議題單全面複測／`RT-0731`＝業主指定黃底部分單獨出報告），否則對外報告會誤述測試範圍。

## 2026-08-01｜截圖要能「向人證明」——整頁截圖裡的關鍵字串等於沒有證據

### 現象
#215（跨日場次前台應顯示結束日期）自動化判定 PASS、斷言正確、整頁截圖也存了，卻被使用者退件：**「截圖沒擷取到關鍵證據，無法證明給人類看」**。補更多圖也救不了——該案本來就只有那 1 張。

### 原因
1. 斷言驗的是 `end_day_str in body_text`（機器可讀），但**證據要給人看**。1440×2078 的整頁圖裡，那行「115年8月2日 下午3:00至8月3日 下午5:00」只佔幾十個像素。
2. 更糟的是**排版二次縮小**：`md_to_docx` 對超長圖以「單頁可用高度 8.6 吋」為上限等比縮。凡 `高/寬 > 1.43` 的圖，實際排版寬度就小於 6 吋；1440×6063 會被壓成**約 2 吋寬**。實測 183 張圖裡有 33 張落在 4 吋以下、5 張不到 2 吋——這些圖在報告上等於不可判讀。

### 對策
- **關鍵證據要近拍**：測試中捲到目標元素再拍一屏（`snap` fixture，`full_page=False`），與案末整頁圖並存 → 一張給脈絡、一張給證據。本案補拍後證據可讀，退件事由才解除。
- 設計案例時就問一句：**「這張圖能不能讓沒跑過測試的人看懂結論？」** 不能就加近拍，別指望整頁圖。
- 交付前用「排版寬度分布」自檢：算 `min(6, 8.6*W/H)` 吋，低於 4 吋的清單列出來檢視。超長手機截圖（480×3227 之類）尤其危險。

## 2026-08-01｜報告產製鏈的兩個靜默失敗：截圖逾時被吞、snap 圖被當成主圖

### 現象
① 某次跑 `--shot=always`，測試 PASS 但 run 目錄**一張圖都沒有**，台帳「截圖」欄是「—」，且**預期／實際也變成「—」**，查不出原因。
② 另一次把只有 snap 圖的 run 匯集進台帳，結果**新增一列垃圾 key** 而不是更新既有列。

### 原因
① `lib/md_reporter.py` 的 `_take_screenshot` 對超長頁 `full_page=True` 會逾時，而 `except: return None` **把例外吞掉**。連鎖效應：`shot=None` 且 `extra_shots` 也空 → `mode == "always"` 才產生的「結果截圖」區被跳過 → 而 `collect_to_review.py` 的預期／實際**只從那區的 `### N.` 段落抓**，於是台帳兩欄變「—」。一個被吞的例外，毀掉三層資訊。
② `collect_to_review.py` 從**第一張截圖的檔名**反推函式名，前提是「第一張＝主圖」。但 PASS＋`failed_only` 模式下**不會有主圖**，`shots[0]` 是 snap 圖（檔名多一段 `__<label>`），剝除 `[chromium].png` 的正規式對不上 → func 變成整串檔名 → 比對不到既有列。

### 對策
- `full_page` 加 `timeout`，逾時**退拍可視區**並把原因印到 stderr；兩者都失敗才回 None。**證據採集失敗必須發出聲音**，不能靜默降級。
- `collect_to_review.py` 先剝掉 `__<label>` 尾段再解析 func：`re.sub(r"(\[[^\]]*\])__.+\.png$", r"\1.png", name)`。
- 通則：**吞例外的 `except: pass/return None` 出現在證據採集路徑上就是 bug**。要嘛往上拋，要嘛降級並留下紀錄。
- 另註：`has_fresh_session` 只看 `.auth/*.json` 的 mtime 搭 `session_max_age_min: 1200`，但 admin JWT 實壽命約 60~85 分鐘（見 2026-07-30 條目），檔案「新鮮」但 token 已死 → Clone API 回 401。長跑前先 `tools/warm_login.py`。

## 2026-08-01｜造態的「場次時間」不會自動平移——來源活動漂進過去會讓整批前台測試在前置全滅

- **現象**：公民態 6 案（IT-10 ac7／IT-11 ac3／IT-12 ac1・ac5／IT-13 ac4／no213）**全部 FAILED，且全卡在同一行**
  `page.get_by_role("button", name="立即報名").first.click()` timeout 30 秒。截圖顯示公民態正常（右上「我的票夾」）、
  活動頁正常載入、畫面上「立即報名」四個字**看得見**。
- **原因**：`ops.make_stage_event` 預設分支（`keep_source_times=False`）只 PATCH 活動窗（`startTime`/`endTime`/`publish*`）
  與 rule（`registrationOpenFrom`/`CloseTo`），**完全不碰 `evEventNodes` 場次時間**。場次就留在來源活動
  （`_STAGE_SOURCE_PKID` 大港閱冰）的絕對日期 **7/18~7/19**，隨時間漂移到過去 → 造出「活動窗在未來（8/11~8/13）、
  場次卻已結束」的**不自洽活動** → 前台場次卡的報名入口從 `<button>` 退化成灰字
  `<span class="text-[#94979B] font-bold ...">`。`get_by_role("button", name="立即報名")` 得 0 個、
  `get_by_text("立即報名")` 得 6 個——**文字在、role 不在**。
- **對策**：預設分支已補場次同步平移（平移量＝活動開始時間位移，維持「場次相對活動開始的偏移」不變）。
  四 stage 驗證自洽：pre_open 場次未來／registration_open 場次未來＋前台按鈕恢復 **6 顆**／in_progress 起已過迄未來／ended 全過。
- **教訓**：
  ① **「整批測試卡在同一個 locator」＝系統性前置問題，不是 N 個各自的缺陷**。先探勘 DOM 事實
  （`get_by_role` 得 0 但 `get_by_text` 得 N ⇒ 元素退化成非互動標籤），不要逐案 debug。
  ② 同類漂移 2026-07-24 已在**活動層與 rule 層**修過，`ops.py` 註解也寫了，但**場次層漏補**——當時 7/18 還在未來所以沒暴露。
  **凡是「複製來源活動再改時間」的造態，時間欄位要全層盤點**（活動窗／曝光窗／rule／場次／EVCredentialSetting 報到窗），
  漏任何一層都是等著引爆的定時炸彈。
  ③ 造態產物要**自洽**：活動在未來、場次在過去這種組合，受測系統的表現不具代表性，跑出來的紅綠都不能用。
- **影響範圍**：所有走 `make_stage_event` 的測試（26 處呼叫）；前台報名鏈測試首當其衝

## 2026-08-01｜跑 QA 一律用預設 local 模式——`TEST_ENV=test` 會讀到空殼 config 並引發連鎖誤判

- **現象**：① OCR warm-login **連續 8 次失敗**，頁面回「登入失敗，請確認帳號、密碼、驗證碼是否正確」；
  ② `has_fresh_session` 判定 admin／citizen 態雙雙過期，據此得出「必須人工重登」的結論並要求使用者做 LINE 手機認證。
  兩者**都是假的**——帳密沒錯、登入態也還在有效期內。
- **原因**：`lib/config_loader.py` 刻意設計成「**非 local 模式只讀 `config.<env>.yaml`，不與 local 合併**」
  （避免 local 蓋掉 QA/PROD 帳密）。而 `config.test.yaml` 從沒填完：`accounts.admin.username` 與
  `event_edit_pkid` 還是 `REPLACE_ME`、`session_max_age_min` 是 30。**兩份 config 的 `base_url` 都指向 QA**，
  所以測試表面上跑得動，錯誤只在帳密、pkid、門檻這些欄位上浮現，極難察覺。
- **對策**：跑 pytest 與 `tools/*.py` **只帶 `$env:PYTHONUTF8=1`，不要帶 `TEST_ENV`**。
  懷疑讀錯檔就跑 `load_config()` 印 `username` 是否含 `REPLACE_ME`、`session_max_age_min` 是不是 30——看到 30 就是讀錯了。
- **教訓**：**OCR 登入失敗別急著重試**（逼近帳號鎖定，且 8 次全錯的機率遠低於「帳密根本不對」）。
  零風險的分流診斷：抓 3 張驗證碼 base64 PNG 存檔，用 `Read` 人工比對 ddddocr 辨識結果——
  本次比對 `1885`／`4687` **全中**，一秒排除辨識問題，直指帳密。改對 config 後 OCR **第 1 發就過**。
- **影響範圍**：所有 session；`config.test.yaml` 若不打算填完，應考慮刪除或加註「未啟用」避免再被誤用

## 2026-08-01｜`xfail(strict, raises=AssertionError)` 遇上「修成 disabled」會判 FAILED 而不是 XPASS

- **現象**：IT-11 ac3（ISS-015 格式錯誤仍可送出）複測判 **FAILED**，錯誤是
  `Locator.click: Timeout` 等 `get_by_role("button", name="確認報名")` 的 *visible, enabled and stable*。
- **原因**：測試寫法是「點送出 → 斷言沒落到成功頁」，並標 `raises=AssertionError`。前端**已經修好**：
  格式錯誤時把送出鈕 `disabled`。按鈕永遠不 enabled → 拋 `TimeoutError` 而非 `AssertionError` → strict xfail 判 FAILED。
  實測三態佐證：填值前 `disabled=False` → 填錯值（格式錯誤紅字 2）`disabled=True` → 改回正確值 `disabled=False`。
- **對策**：**FAILED 不等於「缺陷還在」，也不等於「測試壞了」——修復也可能長成 FAILED**。
  凡 xfail 案複測判 FAILED，先問「是不是系統改成了另一種正確行為，而斷言只認得舊的錯誤行為」。
  斷言要改寫成能表達修復後樣態（此例＝斷言按鈕 disabled），但**移除 xfail 屬定版動作，交使用者裁決**。
- **教訓**：`raises=` 把 xfail 綁死在特定例外型別上，行為一改就漏接。防呆類案例（可送出 vs 鈕 disabled）
  尤其容易踩到——`test_it11_ac4` 早就是「必填空值→鈕 disable」的寫法，同檔內兩案風格不一致就是訊號。
- **註**：同批另撞到 **admin token 約 60 分鐘就失效**（`Clone/EVEvent` 回 401，比 2026-07-30 條目記的 85–90 分鐘更短），
  跑批中途需重刷；`session_max_age_min: 1200` 純粹是檔案新鮮度閾值，擋不住真實 TTL。
- **影響範圍**：所有 `raises=` 綁定的 strict xfail 案；複測／迴歸判讀

## 2026-07-30｜QA 站 backend token 實測壽命約 85–90 分鐘——長跑批前先刷新登入

- **現象**：19 案全量跑批（約 17 分鐘）在第 14 案起連續 6 案 click timeout，失敗截圖＝**登入頁**。
- **原因**：backendtoken 於 warm-login 後約 85–90 分鐘失效（06:37 登入 → 08:03 左右被踢回登入頁；前一晚 21:07 → 隔日 01:35 亦已失效）。`has_fresh_session` 只看檔案 mtime（local 設 1200 分鐘），與後端實際 TTL 脫節。
- **對策**：任何預估 >10 分鐘的跑批，**先跑 warm-login 再起跑**；token 齡 >60 分鐘一律視為不可靠。config.local 的 `session_max_age_min: 1200` 僅是檔案新鮮度閾值，別當成 token 壽命。
- **註**：無人值守登入＝暫時把 `config.local.yaml` 的 `captcha.mode` 切 `ocr` → `tools/warm_login.py --role admin`（ddddocr 在 `.venv`）→ 改回 `manual`。
- **影響範圍**：所有長跑批、夜間排程

## 2026-07-30｜disabled 輸入框可能是生命週期鎖——造態要選對階段，別無限等

- **現象**：IT-05 R3.1/R3.2 對「開放報名時間」datepicker 點擊重試 13 次、等 12 秒仍 `element is not enabled`。
- **原因**：`registrationOpenFrom` 的 `IsDisabled` 綁生命週期鎖 `lock('registrationRules','registrationOpenTime')`（controller L4058）——**報名已開放的活動不允許再改開放時間**，是正確產品行為。受測活動造在 `registration_open` 階段（整體平移後開放報名落在過去），欄位自然永久鎖死。
- **對策**：測「改開放報名時間」類欄位時，基準線把報名窗（連同曝光開始）用 API 推到未來（報名未開放 → 解鎖），見 `test_it05._clean_event(pre_reg=True)`。另注意「短暫 disabled」（存檔後欄位重初始化 1~2 秒）與「永久鎖」樣態相同，先 `_wait_enabled` 等 12 秒再判定屬哪種。
- **教訓**：欄位 disabled 有兩種成因（timing vs 生命週期鎖），先查 controller 的 `IsDisabled` 綁什麼再決定對策；此欄前端**有**消費鎖定值，與 ISS-008「多數元件未消費」並存。
- **影響範圍**：所有需要 UI 改「時間優先序敏感欄位」的測試

## 2026-07-30｜儲存成功判定：toast 單訊號會誤判——改雙訊號（toast ‖ 後端回讀）

- **現象**：IT-05 基準線儲存間歇性「失敗」（07-29 批 2/9、07-30 批 4/19），現場 0 錯誤 0 遮罩、儲存鈕 enabled。
- **原因**：QA 站儲存偶爾 >10 秒才回 success toast；`ops.save()` 只等 5 秒 → 把「慢」誤判成「沒存」。重試再點一次時儲存 in-flight、按鈕 disabled，又衍生 click timeout。
- **對策**：判「儲存成功」用雙訊號：20 秒 toast 窗 ‖ 後端回讀**本次造態的 :37 分鐘值**已入庫（`test_it05._save_with_signals`）。造態值統一用不常見分鐘數讓回讀比對免撞既有資料。
- **教訓**：對外部系統的單一 UI 訊號設短 timeout ＝ 給自己造 flaky；判定訊號要有第二來源，且第二來源要能區分「本次操作」與歷史殘留。
- **影響範圍**：所有依 toast 判存檔成功的測試

## 2026-07-30｜「僅改 rule 欄位儲存無反應」不成立——缺 Banner 事故的衍生誤判

- **現象**：07-26 記錄「EVEventRule 欄位／報到列／單獨改曝光結束按儲存完全無反應」，據此在所有 IT-05 案例加 `_force_dirty` 觸發器並一度開 ISS-022。
- **原因**：該觀察在**缺 Banner 的複製品**上做的——Banner 必填擋住 `runSaveAll`（validateAllRequired 提前 return），且 FileList 必填錯誤走區段 well 非 `.errorText`，於是「怎麼按都沒反應」。跟欄位種類無關。
- **複驗**：20260730 `test_it05_dirty複驗_*` 在有 Banner 的乾淨基準線上僅改截止報名（不加觸發器）→ toast 正常、值入庫。缺口不復現，ISS-022 撤案正確。
- **教訓**：**在受汙染的環境上觀察到的「欄位行為差異」，換乾淨環境必須重驗**；一個根因（缺 Banner）會偽裝成多個不相干症狀（時間規則未實作／儲存無反應／欄位接線缺口），修掉根因後所有衍生結論都要重新來過。

## 2026-07-28｜除錯紀律：先立正向基準，再談根因（8 次誤判的教訓）

### 現象
同一個問題（時間規則測不出防呆）連續宣告 **8 個根因、7 個被自己推翻、第 8 個到停工仍未驗證**。
期間一度在無正向對照下把「5 條規則未實作」寫進問題單與交付報告，靠使用者質疑才攔下。

### 原因（同一個錯誤重複八次，不是八個獨立失誤）
1. 單一觀察就宣告根因，不先設計反證；改完沒好就換下一個假說，把除錯做成猜謎
2. 拿「繞過去了」當「找到了」（加 dirty 觸發器讓值進得去，就當問題解決）
3. **整輪沒有正向對照**——沒先建立「這條規則正常時會亮」的基準，就判「不亮＝未實作」；
   而 7/13 的報告裡**本來就有現成的正向答案**（三條規則的訊息原文）
4. 可信度分級失守：把「原始碼有寫」「實測通過」「我推測」混為一談，還用「已確認」包裝推測
5. 自己再造靜默行為：「已有圖就跳過上傳」的判斷讓整段上傳被略過而不報錯

### 對策（下次動手前先做到）
- **先跑一條已知會成功的正向案當回歸基準**，基準不亮就別碰任何反向案
- 任何假說先問「如果它是真的，我還會看到什麼？」，設計能**否證**它的觀察再改
- 「繞過去」與「找到根因」分開記錄，繞過去的不得作為結論依據
- 判「未實作」前必須同時滿足：基準線可儲存 ✓、同規則正向案會亮 ✓、違規值確認生效 ✓
- 措辭紀律：未經端到端驗證的一律寫「假說」，不寫「已確認」

## 2026-07-13｜「防呆未實作」判定方法論：髒情境 → 乾淨情境 → 隔離驗證（IT-05 翻案）

### 現象
IT-05 三條時間規則在空草稿情境下「儲存無提示」→ 判 xfail「前端未實作」。使用者質疑：畫面上同時有其他檢核（必填紅字）被觸發，可能是「檢核互相壓制」而非未實作。三段驗證後：三案判定全翻修。

### 方法論（判「未實作」前必經三段）
1. **髒情境**（空草稿）：無提示 ≠ 未實作——必填檢核優先執行，必填未過時時間類提示**不顯示**（檢核分層）。
2. **乾淨情境**（全欄位滿足的複製品 `make_stage_event(keep_source_times=True)`，僅造目標違規）：提示出現＝機制存在；但注意出現的可能是**伴生規則**的提示（一個改動常同時違反多條）。
3. **隔離驗證**（把所有伴生規則先「合法化」，讓目標規則成為唯一違規）：此時無提示才可判「該規則未實作」。
IT-05 結果：「截止報名≤截止報到」「場次開始≥活動開始」隔離後無提示＝未實作；「場次結束>開始」乾淨情境有提示＝已實作（原判定誤）。

### 附帶教訓
- **後端 ISO 時間是 UTC**：`datetime.fromisoformat()` 後直接加減會差 8 小時、造出計畫外的伴生違規（ac1d/ac2d 首輪誤觸「截止報到<開放報到」「開始時間往前提早」）——一律 `.astimezone().replace(tzinfo=None)` 轉本地再運算。
- **誤判來源之三：欄位自動帶值**——前台「姓名」自動帶入會員名，「必填空值可送出」實為帶值送出（ISS-016 撤案）；驗空值必先 `fill("")` 清空並斷言 `input_value()==""`。
- **非同步操作「進行中」不得判定**（IT-04 ac6，使用者指正）：上傳類輪詢至終態（成功/錯誤）最長 N 秒；逾時仍 in-progress 本身就是發現，以「逾時卡○○」記錄再判。

## 2026-07-13｜xfail(strict=False) 會把環境錯誤吞成「假 xfail」（圖文不符事故）

### 現象

## 2026-07-12｜給使用者操作的有頭視窗必須可縮放（no_viewport）

## 2026-05-20｜wait_for 的 locator 必須與 DOM 元素類型一致

### 現象
`page.get_by_role("button", name="新增場次").first.wait_for(state="visible", timeout=15000)` 一直耗盡 15 秒再超時，但 DOM 裡確實有「新增場次」元素。

### 原因
STGroupManage 的「新增場次」/ 「批量新增場次」是 `<div>` 元素，不是 `<button>`。`get_by_role("button", name="新增場次")` 在 DOM 裡永遠找不到對應元素，所以 `wait_for(state="visible")` 一定超時，不論等多久。
超時後接著 `page.wait_for_timeout(3000)` 只是盲等，如果 3 秒不夠，元素仍然「不存在」。

### 對策
```python
# 錯誤 — role 不對，永遠 timeout
page.get_by_role("button", name="新增場次").first.wait_for(state="visible", timeout=15000)

# 正確 — 用 get_by_text，直接對 text node 搜尋，與 tag 無關
page.get_by_text("新增場次", exact=True).first.wait_for(state="visible", timeout=15000)
```
**通則**：寫 `wait_for` 前先確認元素是什麼 tag；`get_by_role` 嚴格過濾 ARIA role，`<div>` 沒有 implicit button role。不確定 tag 時，`get_by_text` 是最安全的 fallback。

## 2026-05-20｜診斷腳本：用 page.wait_for_timeout，不用 time.sleep

### 現象
在 `tools/_diag_*.py` 裡用 `time.sleep(3)` 等待頁面渲染，但等完之後 DOM 檢查結果仍是空的（找不到預期元素），和實際頁面不符。

### 原因
`time.sleep()` 是 Python 層的阻塞休眠，會**凍結**整個呼叫執行緒，包含 Playwright 用來處理 browser events（CDP messages）的事件循環。Sleep 期間 browser 發送的任何事件（navigation complete、XHR response、Vue hydration）都無法被 Playwright 接收，頁面狀態無法推進。

### 對策
```python
# 錯誤
import time; time.sleep(3)

# 正確 — Playwright 事件循環繼續運作
page.wait_for_timeout(3000)
```
診斷腳本同樣適用此規則；`wait_for_timeout` 讓 Playwright 在等待期間仍能接收並處理瀏覽器事件。

## 2026-05-18｜md_reporter run_id 碰撞：兩個 pytest 程序同分鐘啟動

### 現象
用 `--shot=always` 跑全套測試（110 tests / 27 分鐘），結束後 `md_to_docx.py` 自動選了「最新」run 目錄，但 Word 報告只含前一次 2-3-13 的 5 筆資料。真正的 110 筆全套結果找不到。

### 原因
`md_reporter.py` 的 `run_id` 是 `datetime.now().strftime("%Y%m%d_%H%M")`（精度：分鐘）。本次全套跑的 **啟動分鐘（23:38）** 和前一次 2-3-13 專跑的啟動分鐘（23:49）不同，所以全套跑的報告其實存在 `20260517_2338_run`。但 `md_to_docx.py` 的 `latest_run_id()` 用 `sorted(runs)[-1]` 取最後一個，字母序 `20260517_2349 > 20260517_2338`，所以拿到了前一次小跑的目錄。

**關鍵：同一分鐘啟動兩個 pytest 程序會直接共用同一目錄並互相覆蓋報告。**

### 對策
1. **轉 docx 時務必指定 run_id**，不要依賴 `latest_run_id()` 自動選取：
   ```powershell
   .\.venv\Scripts\python.exe tools\md_to_docx.py 20260517_2338
   ```
2. 若無法確認 run_id，先用 `ls reports\` + 看截圖修改時間來判斷正確的 run 目錄。
3. 若要在同一分鐘啟動多個 pytest 程序（平行跑不同工項），需先修改 `md_reporter.py` 讓 run_id 加上秒數：`"%Y%m%d_%H%M%S"`，或啟動前手動建立獨立的 reports 子目錄。

## 2026-05-17｜EVEventEdit 頁定位工程方法（一次對，不試錯）

### 根本原則
**每個欄位的 DOM 結構是獨立的，不能跨欄位類推。** 看到欄位 A 有 `<span>*</span>` 不代表欄位 B 也一樣；欄位 C 可能根本沒有 label。唯一正確做法：**先取得 DOM 事實，再寫 selector**。

### EVEventEdit 頁的穩定定位錨點

| 範圍 | 錨點 | 穩定性 | 適用 |
|---|---|---|---|
| 表單欄位 | `data-field-id` | ✅ 跨 deploy 穩定（2026-05-17 重整驗證）| 2-3-8、2-3-9 所有欄位 |
| 區段容器 | `data-anchor` | ✅ | scroll 定位各 section |
| PrimeVue 元件 | `data-pc-name` | ✅ | toggleswitch/select 等元件互動 |
| 填寫建議側欄 | `aside` + `has_text="填寫建議"` | ✅ | 2-3-11 |
| 即時預覽面板 | `[data-preview-panel-root]` | ✅ | 2-3-12 |
| 預覽內容元素 | `data-preview-element` | ✅ | 2-3-12 內容驗證 |

### label 有 `<span>*</span>` 的問題
- **現象**：`get_by_text("label text", exact=True)` 永遠找不到；因為 label 元素的完整文字是 `* label text`。
- **對策**：不靠 label 文字定位，改用 `data-field-id` 定位容器，再在容器內找 `label`：
  ```python
  EVEventEditPage.field_label(page, field_id)
  # 等同於 page.locator(f"[data-field-id='{field_id}'] label")
  ```

### 無 label 的欄位（如 registrantFields）
- inventory 顯示 `label: (無 label)`，代表欄位容器內沒有 `<label>` 元素。
- 只驗容器本身可見：`EVEventEditPage.field_container(page, field_id)`。

### 前置工作：一次跑 inventory 腳本
寫新 EVEventEdit 相關測試前，先跑：
```powershell
$env:PYTHONUTF8=1
.\.venv\Scripts\python.exe tools/inventory_fields.py --out inventory_out.txt   # 主內容欄位
.\.venv\Scripts\python.exe tools/inventory_aside.py  --out aside_out.txt       # aside 結構
```
取得每個欄位的 `data-field-id`、label 真實文字、元件型別後，**對照表建好再寫測試**，不靠 src 推斷。

### aside 範圍注意
- 填寫建議（2-3-11）和即時預覽（2-3-12）在 `<aside>` 裡，不在 `<main>` 裡。
- `inventory_fields.py` 只掃 `main`，不會列出這兩個。需另跑 `inventory_aside.py`。

## 2026-05-15｜PrimeVue Tabs：inactive panel 不渲染 DOM，selector 前必須先 click tab

- **現象**：對 `報名欄位設定` / `憑證與報到管理` 面板內的 label 跑 `get_by_label()`，找不到元素、timeout；`get_by_role("tab", name="報名欄位設定")` 也 timeout。
- **原因**：
  1. **PrimeVue Tabs 的 lazy render**：只有 active tab 的 panel 實際進入 DOM；inactive panel 內容根本不存在。測試直接對 inactive panel 找元素，永遠找不到。
  2. **`get_by_role("tab", name=...)` accessible name 計算問題**：tab button 裡有 SVG icon，accessible name 可能被計算為 SVG content 而非 `<span>` 文字，導致 `name="報名欄位設定"` 匹配失敗。
- **對策**：
  - **測試層**：在 step function 裡先 click tab，等 panel 渲染後再操作：
    ```python
    page.locator("[role='tab']").filter(has_text="報名欄位設定").first.click()
    page.wait_for_timeout(1000)
    ```
    用 `.filter(has_text=...)` 而非 `name=`，因為 accessible name 含 SVG 干擾。
  - **dump 工具層**：`dump_sections.py` 亦改用同樣的 locator 策略（見下條）。
- **通則**：凡是多 tab 頁面，任何 tab panel 內的 selector 在操作前都必須確認 panel 已 active；直接寫 locator 不 click，100% 失敗。
- **適用範圍**：2-3-8 報名欄位設定、2-3-9 憑證與報到管理，以及任何用 PrimeVue `<TabPanel>` 或 `<Tabs>` 的頁面。

## 2026-05-15｜selector 根因分析：src 三種失真來源 + dump 工具法

本條整合「為什麼讀 src 仍然寫出錯誤 selector」的根因，以及已驗證的補充定位方法。

### 根因（三種失真）

| 失真類型 | 現象 | 來源 |
|---|---|---|
| **Tailwind JIT purge** | `.section-list` / `.preview-panel` 在 DOM 消失 | Vue SFC scoped CSS，build 後移除 |
| **i18n key ≠ rendered text** | `Components.STFilter.Apply` 渲染出「套用」非「查詢」 | prop 覆蓋 i18n default |
| **PrimeVue wrapper** | 元件加插 extra div/span，`get_by_role` accessible name 含 SVG | PrimeVue 內部結構複雜化 accessible tree |

以上三種都不出現在 src 裡，只有 **live DOM** 才能確認。

### 改良方法：`tools/dump_sections.py`（Playwright + auth）

- **動機**：人工 dump `page.content()` 太大（整頁 HTML >100KB），AI 難消化；`dump_sections.py` 做定向抓取，只取目標 section 的 outerHTML（前 12000 字元）。
- **已知限制**：
  - 需要 fresh session（先跑 `warm-login`）
  - tab 元素需用 `.filter(has_text=...)` 而非 `get_by_role("tab", name=...)`（SVG 干擾 accessible name）
- **使用方式**：
  ```powershell
  $env:PYTHONUTF8=1
  .\.venv\Scripts\python.exe tools/dump_sections.py <full_url> --out .tmp_dump_out.txt
  ```
  → 輸出各 section 的可見文字清單 + outerHTML 節錄，AI 對著真實 DOM 修 selector。
- **什麼時候用**：pytest 紅，src 讀完還是找不到元素，進入 CLAUDE.md 的「紅了二修」步驟時。

### 結論

- **src** 仍有價值：字面字串（entity name、硬寫的 label）可信；i18n key、CSS class 不可信。
- **DOM dump** 是「紅了二修」的標準工具，不是每次都跑，只在需要時用。
- **flow 不變**，多一個工具：src 解碼 → 寫 selector → pytest → （紅）→ dump DOM → 改 selector。

## 2026-05-14｜filter() 後的 chained locator count() 在 data:svg img 上不穩定

- **現象**：`page.locator("aside").filter(has_text="...").first.locator("ul li a").count()` 回傳 0，但同個 aside 裡的 `get_by_text("...")` 可以找到文字。

- **適用範圍**：凡是在 `filter()` 後繼續 chain CSS selector 並呼叫 `count()` 的情境。

## 2026-05-14｜src 的 CSS class 不能直接當 selector — Tailwind scoped class 在 DOM 中消失

- **現象**：`SectionList.vue` 中寫 `class="section-list"`，用 `page.locator(".section-list")` 找不到元素；`PreviewPanel.vue` 中寫 `class="preview-panel"`，同樣找不到。

  - ✅ 用結構型 selector：`<aside>`、`<ul>`、`<li>` 等 HTML 語意標籤
  - ❌ 不用 src 裡的 CSS class name（`.section-list`、`.preview-panel` 等）當 selector
  - ❌ 不用 img alt（src 寫 `alt="completed"` 但實際 DOM 是 `alt=""`）
- **實例**：2-3-11 `aside.filter(has_text="填寫建議")` 替代 `.section-list`；tick icon 改用 `aside ul li img`。
- **適用範圍**：所有從 Vue SFC src 解碼 class 名稱後直接用作 locator 的地方。

## 2026-04-30｜Token 消耗巨大：AI 試錯法找 Selector

- **現象**：寫完第一批測試案例（2-2-2-B，4 個 case），光是 selector 除錯就幾乎用完一天的 token quota
- **原因**：採用「AI 猜測 selector → 執行失敗 → AI 探查 DOM → AI 修 → 再執行」的迴圈。每輪循環都累積大量 context：
  - Explore 子 Agent 回傳的報告過於冗長（程式碼＋表格＋分析，遠超實際所需）
  - headless DOM 探查腳本輸出大量無關噪音（checkbox 欄位×20）
  - 跨 session 的壓縮摘要本身就很大
  - 每次 pytest 執行輸出 50–100 行
- **對策**：
  1. **人工 inspect 優先**：新頁面先由人用 DevTools 或 `playwright codegen` 點一遍，確認所有 selector，再讓 AI 寫測試邏輯。AI 不應試圖替代這個步驟。
  2. **限制 subagent 回應長度**：呼叫 Explore agent 時明確要求「只回傳關鍵事實，200 字以內」。
  3. **一次報告所有問題**：執行失敗後，人工掃描輸出，彙整成一句話告訴 AI，而非讓 AI 逐一分析每個失敗。
  4. **分離探查與撰寫兩個階段**：先做 selector audit（人工），確認後再讓 AI 一次寫完所有 test file。

## 2026-04-30｜i18n 推斷與實際 DOM 不符

## 2026-04-30｜PrimeVue 元件 ID 不穩定

- **現象**：DevTools「複製 selector」產生的 CSS path 包含 UUID（`#db0482f3-...`）與 `#pv_id_39`，這些 ID 在重新部署或頁面結構變更後會改變

- **對策**：

## 2026-04-30｜UI 自動化測試 ROI 評估

- **現象**：導入自動化後仍需人工點過新頁面（用 codegen 或 inspect），被質疑與手動測試差異何在
- **結論（誠實評估）**：

  | 場景 | 結論 |
  |------|------|
  | 一次性驗收，之後不再迭代 | ❌ 手動測試效益更高 |
  | 每月有新版本上線 | ✅ 第 2 次 deploy 後開始回本 |
  | 只驗「元件存在」（smoke） | ⚠️ 價值有限 |
  | 驗完整業務流程（新增→查詢→驗證） | ✅ 高價值 |
  | 無 CI 整合（手動執行腳本） | ⚠️ 只節省部分時間 |
  | 有 CI（每次 deploy 自動跑） | ✅ 最大效益 |

- **關鍵認知**：自動化測試的效益來自**回歸保護**，不是驗新功能。新功能的 selector discovery（30 分鐘）是一次性入場費；舊功能每次 deploy 不再手動驗，才是持續回報。
- **對策（正確分工）**：
  1. 人工：codegen 點一遍新頁面，取得穩定 selector（每個新功能一次）
  2. AI：用確認的 selector 寫所有測試邏輯（不再做 selector 探查）
  3. CI：每次 deploy 自動執行（沒有 CI 則效益大幅縮減）
- **長期建議**：
  - 前端加 `data-testid` → selector discovery 成本趨近於零
  - 只寫 3–5 個核心 E2E happy path，不追求全 AC 覆蓋
  - 測試覆蓋業務流程（create → query → verify），而非元件存在性

- **影響範圍**：整個 POC 策略方向

## 2026-08-07｜`-webkit-line-clamp` 不產生溢出，`scrollHeight > clientHeight` 判不出截斷

- **現象**：驗「超長名稱是否限兩行加刪節號」，用 `scrollHeight > clientHeight` 判斷，
  桌機版一律回「未截斷」——但畫面明明有 `...`。
- **原因**：`-webkit-line-clamp` 是**改變佈局**（直接只排兩行），不是內容溢出，
  故 `scrollHeight` 等於 `clientHeight`。
- **走過的彎路**：改用 `cloneNode` 複製一份解除 clamp 來量高度——**複製品未完整繼承字體**，
  量出 120 字只需 2 行（實際 5 行），數字明顯不合理才發現。
- **正解**：在**原元素**上暫時把 `webkitLineClamp/maxHeight/height/overflow/display` 解除，
  強制重排後讀 `scrollHeight`，**量完立刻還原**。同一元素、同一環境，數字才可信。
- **附帶教訓**：量出來的數字**先用常識檢查**（120 個中文字不可能在 584 px 寬只佔兩行），
  不合理就是量錯，不要直接寫進報告。
